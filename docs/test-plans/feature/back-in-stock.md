# Test plan: feature/back-in-stock

## Summary

Plant cards now show an **"Only N left"** badge when 1, 2 or 3 plants are left. At 0 the card must show only "Out of stock", never "Only 0 left". The badge sits with the tags under the plant's name and must never cover the photo or the save button. An out-of-stock plant's page now shows **Email me when it's back**: an email field and a **Notify me** button. In-stock plants show no form, and the API refuses their sign-ups. No account is needed. The email must be a full address (`name@example.com`; `a@b` and `name@` are refused). There is one sign-up per email per plant, ignoring letter case, and a repeat is refused with "You're already on the list". After signing up, the page says which address will be emailed. The change adds `POST /api/plants/{plantId}/notify` (`api/src/features/back-in-stock.ts`), `StockBadge` and `NotifyForm` components, and a plant-card slot and a plant-page slot. `docs/features/back-in-stock.md` and the two new CSS modules are covered by these rows. Nothing in `package.json` or config changed, so this plan does not schedule a full-suite run. Expectations below are the documented ones: a failure against the app is a possible finding, not a reason to change the assertion. From reading the diff, several documented rules look unimplemented (badge at 0, badge placement, email format, duplicate refusal). Those rows are expected to expose possible findings. This plan is not approved. Rows Q1–Q5 stay unresolved (`assumed — ask`) and get no test until a human resolves them.
